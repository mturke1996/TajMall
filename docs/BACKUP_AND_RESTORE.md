# النسخ الاحتياطي والاستعادة (Backup & Restore)

## لماذا هذا الملف ضروري

Supabase Free Tier **لا يضمن نسخاً احتياطية تلقائية** (PITR غير متاح إلا في خطط
Pro وأعلى). بما أن هذا النظام يحمل بيانات مالية حقيقية، الاعتماد على توفّر
Supabase وحده دون نسخة احتياطية مستقلة خطر حقيقي: خطأ بشري واحد (حذف جدول،
`UPDATE` بلا `WHERE`، هجرة SQL خاطئة) قد لا يمكن التراجع عنه.

الحل المُطبَّق هنا: نسخة احتياطية تلقائية **يومية** عبر GitHub Actions —
مجانية بالكامل، لا تحتاج خدمة تخزين خارجية.

## كيف يعمل النسخ الاحتياطي التلقائي

الملف [`.github/workflows/backup.yml`](../.github/workflows/backup.yml):

1. يعمل تلقائياً كل يوم في 02:00 (بتوقيت UTC)، أو يدوياً من تبويب **Actions**
   → **Database Backup** → **Run workflow**.
2. يستخدم `pg_dump` للاتصال المباشر (`DIRECT_URL`) وتصدير نسخة كاملة من
   قاعدة البيانات بصيغة مضغوطة (`custom format`).
3. يرفع الملف كـ **Artifact** في نفس تشغيل الـ workflow، ويُحتفظ به 30 يوماً
   تلقائياً ثم يُحذف (حدود GitHub الافتراضية — قابلة للتعديل في الملف نفسه
   عبر `retention-days`، بحد أقصى 90 يوماً على الخطة المجانية لـ GitHub).

### إعداد لازم قبل أول تشغيل

أضف السرّ التالي في **Settings → Secrets and variables → Actions** بالمستودع:

| السرّ        | القيمة                                                                 |
|-------------|-------------------------------------------------------------------------|
| `DIRECT_URL` | من Supabase Dashboard → Settings → Database → Connection string → **Direct connection** (نفس القيمة المستخدمة محلياً في `.env.local`) |

بدون هذا السرّ سيفشل الـ workflow بوضوح مع رسالة توضيحية، لا صمتاً.

## كيف تسترجع نسخة احتياطية

### 1. تحميل الملف

Actions → **Database Backup** → اختر تشغيلاً ناجحاً → **Artifacts** → نزّل
`fluxen-backup-<التاريخ>.zip` وفُك ضغطه (يحتوي ملف `.dump` واحد).

### 2. الاستعادة على قاعدة بيانات جديدة (الأسلوب الموصى به)

**لا تستعد مباشرة على قاعدة الإنتاج الحالية إلا إذا كنت متأكداً تماماً** —
`pg_restore` بلا حذر يمكن أن يُكرِّر البيانات أو يتعارض مع الموجود. الأسلوب
الأسلم:

```bash
# 1. أنشئ مشروع Supabase جديد (أو قاعدة بيانات محلية فارغة للفحص أولاً)
# 2. استعد النسخة إليها
pg_restore \
  --no-owner --no-privileges \
  -d "postgresql://postgres:[PASSWORD]@db.[NEW_PROJECT_REF].supabase.co:5432/postgres" \
  fluxen-backup-2026-07-07T02-00-00Z.dump

# 3. راجع البيانات في القاعدة الجديدة، ثم فقط بعد التأكد بدّل
#    متغيرات البيئة (DATABASE_URL / DIRECT_URL) على Vercel لتشير إليها.
```

### 3. الاستعادة الجزئية (جدول واحد فقط)

```bash
# اعرض قائمة الجداول/الكائنات داخل النسخة
pg_restore -l fluxen-backup-2026-07-07T02-00-00Z.dump > toc.txt

# عدّل toc.txt لإبقاء الجدول المطلوب فقط، ثم:
pg_restore --no-owner --no-privileges -L toc.txt -d "<connection-string>" fluxen-backup-....dump
```

## التوصية للمدى الطويل

إن انتقل المشروع لخطة **Supabase Pro** فعِّل:

- **Point-in-Time Recovery (PITR)** — استرجاع لأي لحظة خلال آخر 7–30 يوماً،
  أدق وأسرع من `pg_dump` اليومي.
- **Daily backups** المدمجة في لوحة Supabase نفسها.

نسخة GitHub Actions هنا تبقى مفيدة كطبقة ثانية مستقلة (لو تعطّل حساب Supabase
نفسه أو حُذف المشروع بالخطأ) حتى بعد الترقية.

## اختبار دوري (مهم)

نسخة احتياطية لم تُختبَر استرجاعها = لا نسخة احتياطية فعلياً. يُستحسن كل
شهرين تقريباً تحميل آخر نسخة وتجربة استعادتها على قاعدة فارغة للتأكد أن
العملية تعمل بالكامل.

## النسخ الاحتياطي المحلي البارد (تطبيق سطح المكتب Tauri)

طبقة **مستقلة** عن GitHub Actions: لقطة كاملة لبيانات الأعمال تُحفظ على جهاز
التشغيل داخل تطبيق **Taj Mall** (Tauri).

| | |
|--|--|
| **المكان** | `%APPDATA%\ly.tajmall.fluxen\backups\` (Windows) |
| **الملفات** | `{id}.sqlite` + `{id}.zip` (JSON محمول) لكل لقطة |
| **متى** | زر «إنشاء نسخة» من `/settings/backup`، أو تلقائياً عند فتح التطبيق (مرة كل 24 ساعة كحد أقصى) |
| **الصلاحية** | `owner` / `admin` فقط |
| **الاستخدام اليومي** | **لا** — التطبيق لا يقرأ من هذه الملفات؛ Supabase يبقى مصدر الحقيقة |

### ماذا يحتوي الأرشيف ZIP؟

- `manifest.json` — المعرّف، الوقت، الصيغة (`fluxen-cold-backup-v1`)، أعداد الصفوف، **بصمة SHA-256 لكل جدول**
  (`tableSha256`)، وبصمة البيانات (`checksum`)، والجداول التي لم تكن موجودة وقت النسخ (`skippedTables`).
- `tables/<table>.json` — كل صفوف الجدول مرتبة بمفتاحه الأساسي، بنفس جودة البيانات الحية.

**التغطية مضمونة آلياً**: كل جدول في المخطط يجب أن يكون في `COLD_BACKUP_TABLES` أو في `BACKUP_EXCLUDED_TABLES` بسبب مكتوب
(`src/lib/backup/tables.ts`)، وفحص CI `npm run verify:backup-coverage` يفشل عند أي جدول جديد منسي. (قبل هذا الفحص كانت شرائح
أسعار الإيجار والجرد وكل جداول الرواتب والإجازات خارج النسخة.) المستثنى الوحيد اليوم: `app_secrets` (أسرار لا تُكتب في ملف).

> **تنبيه**: الملفات **غير مشفّرة** على القرص. احمِ الجهاز (BitLocker على ويندوز) إلى أن يُقرَّر تشفير النسخ
> (قرار 9.4 في [خطة الإصلاح](./REMEDIATION-AND-DEVELOPMENT-PLAN-2026-11-14.md)).

### استعادة طارئة لاستضافة / مشروع Supabase آخر

1. أنشئ مشروعاً جديداً **فارغاً** وطبّق عليه هجرات `supabase/migrations` (والمقترحة التي كانت مطبّقة في الإنتاج).
2. أنشئ مستخدمي Auth المطابقين لصفوف `profiles` (وإلا ظهرت أخطاء FK على `profiles` وأُلغيت الاستعادة).
3. من جهاز فيه Node و`DIRECT_URL` للقاعدة **الجديدة** (اتصال مباشر لا pooler):

```bash
# PowerShell
$env:DIRECT_URL="postgresql://postgres:[PASSWORD]@db.[REF].supabase.co:5432/postgres"

# أولاً: تجربة جافة. تنفّذ التحميل كاملاً ثم تُلغيه، فتظهر كل المشاكل دون لمس القاعدة
npm run backup:restore-cold -- path\to\20261114T120000Z.zip --dry-run

# إن لم تظهر أخطاء، نفّذ الاستعادة الفعلية
npm run backup:restore-cold -- path\to\20261114T120000Z.zip
```

السكربت: [`scripts/restore-cold-backup.mjs`](../scripts/restore-cold-backup.mjs) والمحرّك
[`scripts/lib/cold-restore.mjs`](../scripts/lib/cold-restore.mjs) (يختبره `npm run test:cold-restore` على نسخة معزولة).

**ما يفعله ويضمنه** (كل نقطة كانت عيباً في الأداة القديمة):

| الضمان | التفصيل |
|---|---|
| تحقق من الأرشيف قبل أي شيء | CRC لكل ملف، وبصمة SHA-256 وعدد صفوف لكل جدول مقابل البيان؛ أرشيف مبتور أو معدَّل يُرفض. يقرأ ZIP بنفسه (الأداة القديمة تستعمل `tar` الذي لا يقرأ ZIP على لينكس) ولا يكتب شيئاً على القرص |
| كل شيء أو لا شيء | معاملة واحدة؛ أي خطأ يُلغيها كلها ويُرجع القاعدة كما كانت (الأداة القديمة كانت تطبع «Done» وتخرج بنجاح بعد أن تُلغي كل شيء بصمت). `--allow-partial` وحده يعتمد الجزئي |
| ترتيب صحيح | الجداول تُرتَّب من المفاتيح الأجنبية في القاعدة الهدف نفسها، لا من قائمة يدوية |
| لا تضاعف في الدفتر | مشغّلات الترحيل تُعطَّل أثناء التحميل. بدونه يُعاد ترحيل كل معاملة فتتضاعف قيود اليومية |
| ترقيم سليم | تُحرَّك تسلسلات `number` وغيرها بعد أقصى قيمة مستعادة، فلا تتعارض أول معاملة جديدة |
| لا يمسح بيانات حقيقية | يمسح الجداول المستعادة أولاً (مشروع جديد فيه بذور هجرات تتعارض)، **ويرفض** العمل إن وجد معاملات أو قيوداً أو مطالبات في القاعدة. `--erase-existing-data` صراحةً فقط |
| لا فقدان صامت | عمود في الأرشيف غير موجود في الهدف، أو جدول غير موجود، يُفشل الاستعادة بدل إسقاط بياناته |
| تحقق بعد التحميل | عدد صفوف كل جدول في القاعدة = المحمَّل |

رموز الخروج: `0` نجحت · `1` خطأ استعمال أو ملف أو اتصال · `2` فشلت وأُلغيت · `3` جزئية (`--allow-partial`).

هذا مسار **هجرة / كارثة** فقط — ليس بديلاً عن العمل اليومي على Supabase، وجرّبه على قاعدة فارغة مرة كل شهرين على الأقل.

### تقوية غلاف سطح المكتب (ما تغيّر في W0)

- كل أمر يستدعيه الموقع (`save_cold_backup`، `export_backup_copy`…) يحتاج صلاحية صريحة في `src-tauri/capabilities/default.json`،
  والإنتاج لا يمنح الصلاحيات إلا لنطاق الإنتاج `https`؛ ملف `dev.json` (localhost) لا يُشحن، ويُفعَّل فقط بـ `npm run tauri:dev`.
- معرّف النسخة المُرسَل من الصفحة يُتحقق من شكله (`YYYYMMDDTHHMMSSZ`) قبل بناء أي مسار؛ وأسماء الجداول كذلك.
  (كان `export_backup_copy` يبني المسار من نص الصفحة مباشرة.)
- الكتابة بأسماء مؤقتة ثم إعادة تسمية: لا نسخة نصف مكتوبة في الفهرس. الفهرس يُستبدل ذرّياً، والتالف يُحفظ `index.corrupt.json` بدل أن
  يُمحى. نسختان في الثانية نفسها لا تكتب إحداهما فوق الأخرى. بصمة البيانات تطابق الملف (كانت تُحسب قبل تعديل الملف فلا تطابقه أبداً).
- نسخة واحدة فقط من التطبيق (`single-instance`)، ومصافحة إصدار `get_shell_info` بين الغلاف والموقع.
- `Cargo.lock` أصبح مُتتبَّعاً (كان مُتجاهَلاً فلا بناء قابل للتكرار)، وسير عمل `desktop.yml` يبني ويختبر على Linux وWindows.
